# Owner and design questions

Part of the [slice design](README.md). Each item is a choice the approved
intent does not settle. Implementers follow the **recommended default** until
the owner (product meaning) or orchestrator (engineering) records otherwise in
[OWNER-DECISIONS.md](../OWNER-DECISIONS.md) or the run plan. "Owner" items
change product behavior; "design" items are engineering defaults the
orchestrator may accept.

| Q-1 | How are folders grouped into one addon package? | Union of shared external id, hard dependency whose stem prefixes the dependent's name, `X_`/`X-` name prefix, and the `Family` edge (prefix without separator, stem ≥ 5 chars, no differing external ids: `Questie`/`QuestieDB` grouped). Over-grouping preferred to mixing parts; edges shown in explanations; a grouping change yields new package hashes (revised in retry 1, M-04) | owner | [domain.md](domain.md) §5 |
| Q-2 | When the winning version of a package lacks a folder this computer has (or vice versa), what happens? | Not installed: a candidate must contain every folder of the **group-wide** package membership (the union over all computers), otherwise the package is `NeedsDecision(PartialCandidate)` on every computer, including computers that have none of its folders; nothing is changed or removed and the decision is shown with folder lists. Consequence: a suite whose new release intentionally drops a folder stays a decision until the uninstall design exists. Removal waits for the uninstall design (revised in retry 1, M-04; group-wide completeness in retry 2, R-M04) | owner | [domain.md](domain.md) §6 |

## Slice limitations (retry 2)

Narrowed behaviour chosen over added machinery; each needs a later decision
before release.

| Limitation | Q |
|---|---|
| Runs only on installs carrying the synthetic marker | Q-24 |
| Folders with any suffixed toc are never transferred, for every client | Q-3, Q-20 |
| A package whose candidate lacks any group-wide member folder is a decision everywhere, also on computers without the package | Q-2 |
| Every publish re-hashes every referenced existing object | Q-7 |
| Any existing journal blocks all new applies on that computer; `needs_help` is resolved later via GUI | Q-25 |
| A crash after the last commit rename but before `committed` is recorded rolls the package back (new content is re-applied next cycle) | Q-25 |
| Online-only or recall-flagged provider entries (files and directories) are refused, never hydrated | Q-6, Q-23 |
