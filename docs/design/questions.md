# Owner and design questions

Part of the [slice design](README.md). Each item is a choice the approved
intent does not settle. Implementers follow the **recommended default** until
the owner (product meaning) or orchestrator (engineering) records otherwise in
[OWNER-DECISIONS.md](../OWNER-DECISIONS.md) or the run plan. "Owner" items
change product behavior; "design" items are engineering defaults the
orchestrator may accept.

| # | Question | Recommended default | Who | Used in |
|---|---|---|---|---|
| Q-1 | How are folders grouped into one addon package? | Union of shared external id, hard dependency whose stem prefixes the dependent's name, `X_`/`X-` name prefix, and the `Family` edge (prefix without separator, stem ≥ 5 chars, no differing external ids: `Questie`/`QuestieDB` grouped). Over-grouping preferred to mixing parts; edges shown in explanations; a grouping change yields new package hashes (revised in retry 1, M-04) | owner | [domain.md](domain.md) §5 |
| Q-2 | When the winning version of a package lacks a folder this computer has (or vice versa), what happens? | Not installed: a candidate must contain every folder of the **group-wide** package membership (the union over all computers), otherwise the package is `NeedsDecision(PartialCandidate)` on every computer, including computers that have none of its folders; nothing is changed or removed and the decision is shown with folder lists. Consequence: a suite whose new release intentionally drops a folder stays a decision until the uninstall design exists. Removal waits for the uninstall design (revised in retry 1, M-04; group-wide completeness in retry 2, R-M04) | owner | [domain.md](domain.md) §6 |
| Q-3 | For `wowf`, which `.toc` does the client load: `_Forever`, `_Camelot`, plain? | Unknown until an **owner-run client check** (e.g. a test addon with differing tocs). Until then the slice uses `validated-plain/1` for `wowf` too: only folders with a plain toc and no suffixed toc are eligible. The `profile:wowf/1` rule (Forever, then Camelot, then plain; Forever/Camelot disagreement fails closed) is specified for a later run and is unreachable in the slice (revised in retry 2, R-M03) | owner | [domain.md](domain.md) §2.1, §3 |
| Q-4 | If WoW starts while a package is being committed, roll back or complete? | Neither while WoW runs: stop with **no further game-file change** (no rollback), keep journal and all copies, show "Waiting — will restore after WoW exits". After a fresh not-running observation, roll the package back (`committing`) or verify it (`committed`). The mixed state while WoW runs and the launch-between-check-and-rename window are reported residual races (revised in retry 1, B-01; replaces the earlier "roll back immediately") | owner | [apply.md](apply.md) §2.3, §4 |
| Q-5 | May the app read AddOns and publish while WoW is running? | Yes (reads only; SPEC blocks only game-file changes). Unstable files defer publishing | owner | [apply.md](apply.md) §1 |
| Q-6 | Should the app force-download (hydrate) online-only provider files? | No. Treat them as not yet available and wait; user can make the folder "available offline" in Dropbox | owner | [adapters-api.md](adapters-api.md) §5 |
| Q-7 | Provider storage: per-file blobs, no compression, no garbage collection in the slice? | Yes for the slice; GC/retention of unreferenced blobs must be designed before release (R-14). Every referenced object that already exists is **re-hashed on every publish** (no size/mtime cache); cost is proportional to package size and is acceptable for synthetic slice data; a verified cache needs its own design before real-size use (retry 2, R-M05) | design | [publication.md](publication.md) §4, §5 |
| Q-8 | Provider-tier test data size and location | Synthetic only, ≤ 50 MB per run, under `D:\Dropbox\Gaming Sync\WoW Sync Test\<run-subdir>`, removed afterwards | owner | [tests.md](tests.md) §4 |
| Q-9 | Where do staging, journals and recovery points live? | `<variant>\.wowsync\` (same volume as AddOns, outside the AddOns folder so WoW does not see them) | owner | [apply.md](apply.md) §2 |
| Q-10 | Are semver-like, dotted-numeric and git-describe labels one comparable family? | Yes (spike data shows authors move between them); unknown pre-release words stay ambiguous | owner | [domain.md](domain.md) §4 |
| Q-11 | Must `.product.db` also agree for variant validation? | Not in the slice (binary format); `.flavor.info` + `.build.info` must agree. Revisit if a client is found where they diverge | design | [domain.md](domain.md) §2 |
| Q-12 | Which product codes are "known"? | Only `wowf` (Forever). Every other client, including retail/classic, goes through guided unfamiliar-client confirmation until a profile is verified | owner | [domain.md](domain.md) §2 |
| Q-13 | Record compatibility | Unknown fields ignored within a schema major; unknown major refused and shown as "written by another app version" | design | [publication.md](publication.md) §2 |
| Q-14 | Non-ASCII addon folder/file names | Unsupported in the slice (listed, never transferred). Needs a Unicode normalization/case-fold design before release | owner | [domain.md](domain.md) §5 |
| Q-15 | Quiescence window | Files modified in the last 2 s, or changed while hashed, make the folder unstable for this cycle | design | [apply.md](apply.md) §5 |
| Q-16 | Processes the app cannot inspect (access denied) | **Block** (`Unknown`) when an uninspectable process's executable name is `wow*.exe` or matches an `.exe` in the variant folder; ignore other uninspectable processes but count them in diagnostics. A renamed client outside the variant folder run elevated is not detected (stated limitation). Revised in retry 1 (M-06) from "never block" | owner | [adapters-api.md](adapters-api.md) §6 |
| Q-17 | Windows-only tests are listed under tier `native`, which `verify` does not execute yet | Keep them `native`; R2-check verifies them from the Windows `cargo test` output and records each name as passed/failed; provider tests that print `BLOCKED` are recorded BLOCKED, never passed. A later packet makes `native` executable in xtask | design (orchestrator) | [tests.md](tests.md) §1 |
| Q-18 | Recovery points are local-only (not uploaded) in the slice (P1-map Q2) | Yes; group-wide rollback is out of slice and will need its own design | owner | [apply.md](apply.md) §2 |
| Q-19 | Process model | One process (GUI + background sync thread) for the slice, per S-mem option 1; not a release decision | design | [crates.md](crates.md) §1 |
| Q-20 | Which `.toc` does the client load when suffixed tocs exist? | Unknown without a verified profile, so for **every** client in the slice (including `wowf`, see Q-3) only folders with a plain toc and **no** suffixed toc are eligible (mapping `validated-plain/1`); other folders are listed as blocked (`UnvalidatedTocMapping`) and never transferred. New in retry 1 (M-02/M-03); extended to all clients in retry 2 (R-M03) | owner | [domain.md](domain.md) §2.1, §3 |
| Q-21 | May an addon version move between computers whose client build differs? | No automatic install: a candidate from a different `build_version` (or different toc mapping) is `NeedsDecision(DifferentClientBuild/DifferentTocMapping)`. Safe but may block during staggered patch days; revisit with an owner-approved compatibility rule. New in retry 1 (M-03) | owner | [domain.md](domain.md) §6 |
| Q-22 | Manual edits that change content but not the version label | Indistinguishable from an author update with the same label: same label + different content is `Ambiguous`; a manual edit that also bumps the label wins as "newer". The slice makes **no provenance claim**: it runs only on synthetic installs (Q-24), so real-data behaviour waits for this decision. New in retry 1 (M-03); scoped by Q-24 in retry 2 | owner | [domain.md](domain.md) §4 |
| Q-23 | Which provider reparse states are safe? | Under the provider root only: cloud-file tag family (`0x9000xx1A`) accepted when the entry is available. An entry (file **or directory**) whose enumeration attributes carry `RECALL_ON_OPEN`, `RECALL_ON_DATA_ACCESS` or `OFFLINE` is refused as not available (Q-6) and never opened or enumerated; attributes come from parent-directory enumeration only, opens add `FILE_FLAG_OPEN_NO_RECALL`. Links, junctions and other tags refused everywhere. Meaning of `PINNED`, Dropbox online-only behaviour and the effect of `OPEN_NO_RECALL` are unverified until an owner-prepared online-only file exists (provider test BLOCKED otherwise). New in retry 1 (M-01); revised in retry 2 (N-02) | design (owner confirm) | [adapters-api.md](adapters-api.md) §2, §5 |
| Q-24 | May the slice touch a non-synthetic (real) WoW install? | **No.** Enrollment requires the marker file `<install root>\.wowsync-synthetic` (first line `wowsync-synthetic/1`) written only by `testkit::SyntheticInstall`; a variant without it is `Unsupported(NotSyntheticInstall)`. Real-data use waits for Q-3, Q-22 and an owner-approved release gate; the marker gate is removed only by an explicit later decision. New in retry 2 (R-M03) | owner | [domain.md](domain.md) §2.1 |
| Q-25 | What happens while an interrupted or `needs_help` operation exists? | While **any** apply journal exists on a computer, no new apply is planned there for any package (publishing continues); recovery settles `staging`/`committing`/`committed` ops when WoW is not running; `needs_help` ops keep journal, staging and recovery slots untouched and show "Needs help" with the reason. Resolving `needs_help` is a GUI flow outside the slice. New in retry 2 (N-01/N-03) | owner | [apply.md](apply.md) §1, §2.5 |

## Slice limitations (retry 2)

Narrowed behaviour chosen over added machinery; each needs a later decision
before release.

| Limitation | Q |
|---|---|
| Runs only on installs carrying the synthetic marker | Q-24 |
| Folders with any suffixed toc are never transferred, for every client | Q-3, Q-20 |
| A package whose candidate lacks any group-wide member folder is a decision everywhere, also on computers without the package | Q-2 |
| Every publish re-hashes every referenced existing object | Q-7 |
| Any existing journal blocks all new applies on that computer; `needs_help` is resolved later via GUI | Q-25 |
| A crash after the last commit rename but before `committed` is recorded rolls the package back (new content is re-applied next cycle) | Q-25 |
| Online-only or recall-flagged provider entries (files and directories) are refused, never hydrated | Q-6, Q-23 |
